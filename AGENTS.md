# sonar

A Claude Code plugin that searches everything a session can reach for what the
user is after. It answers fast with shallow matches, keeps searching deeper
(sibling repos, git history, links, past transcripts) while the conversation
goes on, and hands over what else turned up when the next turn starts.

## Layout

```text
plugin.yml           the plugin's descriptor; plugin.json is generated from it
scripts/sonar        the CLI (Python 3, stdlib only): pulse, shallow, deep,
                     hook, status. Every caller goes through it
skills/pulse/        /sonar:pulse: picks the terms, runs `sonar pulse`, reports
hooks/hooks.yml      the hooks' source of record; hooks.json is generated
tests/               unittest suite for the CLI (`just test`)
docs/                sonar's own docs site; hand-written pages are tracked,
                     the rest is rendered by `just docs`
.github/workflows/   shipyard's project, docs deploy, and release workflows
```

## Working on it

`just` lists the recipes. `just try` opens a session with this checkout loaded
as a plugin; `just test` runs the CLI's tests; `just validate` checks it the way
CI does.

How a pulse flows: `sonar pulse` reads the session's own transcript for the
files it loaded (Read, Edit, and Write targets, @-mentions; paths only, never
tool output), searches those first, then the repo, and prints the shallow
matches, a loaded file winning ties. It then starts `sonar deep --session <id>`
detached, so the skill's Bash call returns at once and no background-task
notice wakes the agent. The deep pass picks a few topic words (TF-IDF over the
lines around the matches against a sample of the repo), walks two hops of
references out from the matched files (links, imports, paths in the text),
then searches links, git history, past sessions, and sibling repos. It writes
`<session id>.json` under the plugin data dir after each stage. A deep hit
needs two terms, at least one of them the user's; a topic word can be the
second but never the only one. Topic words are used for the hops only. The
UserPromptSubmit hook reads that file on the next prompt, hands over what is new as
additional context, and records what it handed over in `<session id>.delivered`.
The state dir derives from the script's own location, never from
`CLAUDE_PLUGIN_DATA`, which only hooks receive. `sonar status` shows where a
session's search stands.

## Conventions

- This is a public repo: no internal hosts, private paths, or company names in
  committed files.
- `plugin.yml` is the source of record for metadata. `.claude-plugin/plugin.json`
  and `plugin.yml`'s `suite.describe` block are generated by shipyard's project
  job; don't edit them by hand.
- Every command is namespaced `sonar:<skill>`.
- Every snippet sonar prints goes through `redact()` and is capped at
  `SNIPPET_MAX`. New sources must do the same.
- sonar reads; it never moves or rewrites what it finds. Where content should
  live is cleat's call, so sonar announces what it found and cleat (or the
  agent) decides what to do about it.
